# 01. 현재 상태 감사

기준일: 2026-07-18  
주의: 공개 콘텐츠와 노트북의 호출 횟수는 실제 사용자 텔레메트리가 아니라 저장소 내부 사용 흔적이다.

## 1. 요약 판정

| 영역 | 판정 | 근거 |
|---|---|---|
| 엔진격 폴더 구조 | 유지 | 실제 책임과 소비자가 존재하고 경계가 유효함 |
| 내부 레이어 규율 | 유지 | import 방향, 테스트 경계, 순환 참조 방지에 필요함 |
| README 레이어 설명 | 축소 및 이동 | 사용자 작업보다 구현 구조를 먼저 설명함 |
| 공개 렌즈 5개 | 개별 강화 | 서로 다른 질문, 데이터, 검증법을 가짐 |
| 147개 축 | 수평 확장 중단 | 대표 제품 경험과 의미 검증보다 축 수가 앞섬 |
| Story와 Simulate | 유지하되 후순위 | 하위 렌즈 계약 안정화가 선행돼야 함 |
| 활성 mainPlan 28개 | 통합 필요 | 완성보다 병렬 확장을 유도함 |

## 3. 내부 기반 패키지는 죽은 엔진이 아니다

외부 importer 파일 수를 확인하면 다음과 같다.

| 패키지 | 외부 importer 파일 수 | 판정 |
|---|---:|---|
| frame | 33 | 비교 프레임 기반으로 실제 사용됨 |
| synth | 105 | 다수 상위 기능의 조합 기반으로 실제 사용됨 |
| reference | 10 | 근거 및 참조 기능으로 실제 사용됨 |

따라서 이 폴더들을 공개 제품 수와 동일시해서는 안 된다. 엔진격으로 분리된 내부 bounded context이며, 폴더 구조를 없애면 책임 경계와 변경 영향이 오히려 불명확해진다.

## 4. 공개 엔진의 무인자 동작

| 호출 | 현재 기본 반환 | 제품 판정 |
|---|---|---|
| `dartlab.scan()` | 27축 안내표 | 탐색에는 유용하나 첫 결과는 아님 |
| `dartlab.analysis()` | 22축 안내표 | 축 선택을 사용자에게 넘김 |
| `dartlab.credit()` | 8축 안내표 | 루트와 Company 기본 경험이 다름 |
| `Company.credit()` | 8축 안내표 | 루트와 마찬가지로 기본 호출은 가이드 |
| `Company.credit("등급")` | 집계 dCR 등급 | Credit 대표 제품으로 강화할 기존 진입점 |
| `dartlab.quant()` | 48축 안내표 | 넓지만 대표 질문이 약함 |
| `dartlab.macro()` | 15축 안내표 | 지표와 축 안내가 전달경로보다 앞섬 |
| `dartlab.industry()` | 34개 산업표 | 루트는 산업 탐색 역할 |
| `Company.industry` | 가치사슬 위치, 단계, 피어 등 실제 결과 | 좋은 기본 제품 형태 |

핵심 문제는 깊은 렌즈가 불필요하다는 것이 아니다. 사용자가 깊은 렌즈에 들어갈 때 다시 축을 설계해야 한다는 것이다.

## 6. 테스트 깊이

패키지 소스 대비 관련 테스트 줄 수의 단순 비율은 다음과 같다. 절대 품질 점수가 아니라 상대적 검증 밀도를 보는 참고치다.

| 엔진 | 테스트 비율 | 해석 |
|---|---:|---|
| simulate | 0.54 | 계산 및 시나리오 기반 검증이 상대적으로 강함 |
| credit | 0.30 | 기본 제품과 검증이 비교적 밀접함 |
| industry | 0.24 | 규모 대비 검증은 보통 |
| scan | 0.23 | 실제 축과 스크리너 경로가 비교적 잘 검증됨 |
| quant | 0.21 | 축 수와 범위에 비해 대표 의미 검증이 더 필요함 |
| analysis | 0.19 | 사용 흔적은 높지만 넓은 범위에 비해 얕음 |
| macro | 0.08 | 다섯 렌즈 중 가장 우선적인 검증 보강 대상 |

공식 product smoke도 표면 노출과 비어 있지 않음을 주로 확인한다.

- Scan은 27개 축을 실제 호출한다.
- Analysis는 Company 경로에서 일부 대표 축만 실제 호출한다.
- Credit은 기본 집계 결과를 실제 호출한다.
- Quant와 Macro는 무인자 안내표를 확인하는 데 그친다.
- Industry와 Story는 실제 결과 경로를 호출한다.

따라서 다음 단계에는 공개 표면 회귀 게이트와 별도로 의미 제품 게이트가 필요하다.

## 7. 저장소 내부 사용 흔적

블로그 직접 호출 및 언급의 상대 분포는 다음 방향을 보인다.

- Analysis가 압도적으로 많고 약 20개 축이 사용된다.
- Analysis 상위 10개 축이 전체 호출의 약 89%를 차지한다.
- Credit은 대부분 등급이라는 하나의 대표 질문으로 사용된다.
- Quant는 종합, 판단, 지표, 변동성 등에 집중된다.
- Macro는 블로그 직접 호출이 없다.
- Industry는 실제 기본 결과가 있으나 노출이 매우 적다.

이 자료는 외부 사용자 행동을 증명하지 않는다. 다만 내부 제작자조차 전체 축보다 소수 대표 질문을 반복 사용한다는 점을 보여준다.

## 8. README와 제품 표면

현재 README는 약 800줄이며 다음 정신모형이 중첩된다.

- Terminal 우선
- 세 가지 시작점
- AI, Python, CLI
- 세 개 분석 레이어
- Company, Gather, Scan, Analysis, Quant, Credit, Macro, Industry, Story 등 다수 기능
- Search, Channel, EDGAR, MCP, Skill OS, lite, OpenAPI

UI와 landing도 map, scan, terminal, universe, viewer, report, industry, lab, playground 등 다수 route로 나뉜다. 반면 Analysis, Credit, Quant, Macro, Industry는 일관된 렌즈 제품군으로 설명되거나 개별 대표 경험을 갖지 못한다.

## 9. API 구조 부채

루트 API는 모듈을 callable로 패치하는 편의 계약을 사용한다. 동시에 `src/dartlab/api.py`에는 IDE와 타입 검사에 적합한 명시적 typed API가 존재한다.

이중 경로는 장기적으로 설명과 도구 지원 비용을 만든다. 그러나 현재 최우선 문제는 API 형식 통일이 아니라 렌즈별 대표 결과와 의미 계약의 부재다. API 대정리는 제품 계약이 안정된 뒤 수행한다.

## 10. 최종 진단

DartLab은 구조가 과한 것이 아니라 다음 상태다.

**수평 능력은 과잉이고 수직 제품 완성은 부족하다.**

따라서 해결책은 폴더 삭제나 엔진 비공개화가 아니다.

- 구조는 유지한다.
- 공개 렌즈 정체성을 강화한다.
- 축 추가를 멈춘다.
- 대표 질문을 먼저 완성한다.
- 상위 워크플로가 렌즈 결과를 재사용하게 한다.
- 제품 계획 수를 줄이고 실행 순서를 강제한다.
