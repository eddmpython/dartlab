## 1. 사상

브라우저에서 **실제로 도는 것만** 가르친다. 안 되는 것은 감추지 않고 그 자리에서 밝히고,
`pip install dartlab` 이후 열리는 로컬 코스로 정직하게 분리한다.

편수를 채우려고 능력 하나를 한 편으로 기계 분할하지 않는다. 편은 **사람의 질문**으로 선다.
"잘 벌고 있나", "돈 떼일 위험은 얼마인가", "이 숫자는 어디서 왔나". 능력 이름이 제목이 되는 순간
그것은 도감이지 이야기가 아니다.

5편까지는 입구다. 6편 이후부터는 세밀함을 운영 규칙으로 둔다.
기능 하나를 한 편으로 소개하지 않는다. 한 편은 독자가 실제로 막히는 오해, 실패, 기준 차이 하나를 깊게 푼다.
각 편은 반드시 초보자의 오해, 코드나 표에서 보이는 증상, 원인, 확인 방법, 고치는 순서, 행동 검사를 가진다.
세밀함은 긴 설명이 아니라 실패 지점의 원인과 고치는 순서를 분해하는 것이다.

`panel` 이 dartlab 사상의 정본이다.
재무제표, 정형공시, 사업보고서 본문을 모두 `c.panel(topic)` 이라는 한 표면으로 눕힌다.
초보자에게 중요한 것은 행열 크기가 아니라 화면에 보이는 실제 계정, 기간, 값, 공시 문장이다.
`.shape`, "몇 행 몇 열"은 내부 검증 신호이지 독자에게 줄 학습 목표가 아니다.
새 편은 먼저 "이 표에서 어떤 계정과 기간 값이 보이는가"를 보여 준다.
`select` 는 별도 설명 주제가 아니다. 필요한 줄을 좁힐 때 한 줄로 쓰면 된다.
`trace` 도 주연이 아니다. 출처가 헷갈리거나 자동 분석을 검산할 때 쓰는 점검 도구다.

DART만 가르치지 않는다.
`Company("005930")` 과 `Company("AAPL")` 은 같은 facade 의 다른 provider다.
한국은 DART 사업보고서와 분기보고서, 미국은 EDGAR 10-K 와 10-Q 로 원천이 다르지만 독자는 같은 질문을 던져야 한다.
커리큘럼은 개념을 잘게 쪼개되, 각 개념마다 "DART에서는 이렇게 보이고 EDGAR에서는 어디까지 같은가"를 확인한다.
EDGAR narrative topic 이 브라우저에서 확인되지 않은 경우에는 재무 panel 동형성까지만 가르치고, 본문 섹션은 경계로 남긴다.

독자용 문구에 "축"(axis)이라는 말을 쓰지 않는다. 내부 용어다.
내부 기능 개수, 인증 개수, n/n 점검 표현도 쓰지 않는다. 중요한 것은 독자가 실제로 여는 표, 계정, 기간, 값, 공시 문장이다.

## 3. 학습 계단

한 편은 기능 소개가 아니라 **다음 편을 읽을 자격을 만드는 작은 계단**이다. 각 편은 선행 상태,
새로 얻는 능력, 넘어가는 행동 검사를 가져야 한다. 행동 검사를 못 만들면 단독 편으로 세우지 않는다.

6편 이후 모든 편은 **오해 단위**로 선다. 기능명은 내부 분류일 뿐 제목이나 본문 중심이 되면 실패다.
기획 루프는 새 능력뿐 아니라 실패 장면, 오독 방지, 원천 확인, 행동 검사를 함께 승인해야 한다.

개념은 다음 단위보다 크게 묶지 않는다.

1. **식별자**: DART 6자리 종목코드, EDGAR ticker 또는 CIK.
2. **provider**: 같은 `Company` facade 가 DART와 EDGAR 중 어디로 라우팅되는가.
3. **표면**: `panel()` 전체가 무엇을 담고, `panel(topic)` 이 무엇을 좁히는가.
4. **재무제표**: IS, BS, CF가 같은 기간 격자로 눕는다는 사실.
5. **기간**: Y, Q, 10-K, 10-Q의 리듬과 기준일 차이.
6. **본문**: 사업의 내용, 위험, 경영진단, 주석 같은 narrative 영역.
7. **행 정체성**: `chapter`, `sectionLeaf`, `blockLeaf`, `snakeId`, `항목` 같은 위치 정보.
8. **필요한 줄 찾기**: panel 에서 계정 후보를 먼저 보고, 필요한 순간에만 `select` 로 좁힌다.
9. **검산**: 직접 계산, 빈칸 해석, 연결과 별도, 단위 확인.
10. **근거 확인**: 원 표, 공시 본문, 원천 링크, 자동 분석의 입력을 확인한다. `trace` 는 보조 도구다.

한 편은 위 개념 중 하나를 중심 질문으로 삼고, 필요한 경우 마지막 절에서 DART와 EDGAR의 차이를 짧게 비교한다.
두 provider 에서 모두 실측되지 않은 호출은 "같다"고 쓰지 않고, 확인된 범위와 미확인 범위를 분리한다.

| 편 | 선행 상태 | 새 능력 | 넘어가는 행동 검사 |
|---|---|---|---|
| 1 | 없음 | 공시가 `panel` 과 `scan` 으로 바뀐다는 전체 그림 | `005930` 과 `AAPL` 이 모두 회사 입력값이 될 수 있음을 말한다 |
| 2 | 회사 하나를 만들 수 있음 | DART 회사의 `panel` 이 재무제표와 사업보고서 본문을 함께 담는 단일 표면임을 안다 | `panel("IS")` 앞줄에서 계정과 기간 값이 보인다고 말한다 |
| 3 | 본문 코드를 눌러 봄 | 셀 순서, 재실행, 노트북 생성의 상태 모델 | 새 셀을 추가해 앞 셀 변수를 재사용한다 |
| 4 | 코드로 회사를 열 수 있음 | DART 6자리 코드와 EDGAR ticker 가 모두 Company 식별자임을 안다 | `Company("005930")` 과 `Company("AAPL")` 의 시장 차이를 설명한다 |
| 5 | `panel` 이 단일 표면임을 앎 | `freq="Y"` / `"Q"` 로 질문의 시간 간격을 바꾼다 | 같은 계정을 연간과 분기로 열고 질문 차이를 설명한다 |
| 6 | DART panel 기간 감각이 있음 | DART와 EDGAR가 같은 `Company.panel("IS")` 표면으로 재무제표를 돌려준다는 점 | 삼성전자와 Apple 표의 계정, 기간, 통화 차이를 말한다 |
| 7 | EDGAR 회사도 열 수 있음 | EDGAR 10-K, 10-Q 리듬과 USD 기준을 재무 panel 위에서 읽는다 | `AAPL` IS, BS, CF의 앞줄을 보고 DART와 같은 점과 다른 점을 말한다 |
| 8 | 전체 panel 을 볼 수 있음 | `chapter`, `sectionLeaf`, `blockLeaf` 로 DART 사업보고서 안의 위치를 찾는다 | `panel("사업")`, `panel("주석")`, `panel("임원")` 이 다른 행 묶음임을 확인한다 |
| 9 | 사업보고서 섹션을 찾을 수 있음 | 사업의 내용, 제품, 원재료, 생산설비, 직원 같은 비재무 본문을 panel 로 읽는다 | 사업 설명 한 문장을 재무 숫자가 아니라 공시 본문 근거로 인용한다 |
| 10 | 비재무 본문을 읽을 수 있음 | 주석 상세가 재무 숫자의 원인을 설명하는 층임을 안다 | `panel("재고")` 또는 `panel("차입")` 결과를 BS 숫자와 연결한다 |
| 11 | panel 검색으로 계정 후보를 볼 수 있음 | 매출액이 안 보일 때 계정 이름 차이와 빈 결과를 해석한다 | 빈 결과를 보고 오류인지 계정명 차이인지 말한다 |
| 12 | 필요한 줄을 좁힐 수 있음 | 파이썬으로 직접 계산 | 매출액과 영업이익으로 마진을 계산한다 |
| 13 | 직접 계산한 숫자가 있음 | 표와 본문을 함께 놓고 짧은 분석 문장을 만든다 | 계산한 마진 문장 옆에 사용한 표와 기간을 적는다 |
| 14 | 회사 숫자와 본문을 손으로 볼 수 있음 | 인자 없는 호출로 가능한 질문 목록 확인 | analysis, scan, credit, macro 의 목록 패턴을 일반화한다 |
| 15 | 질문 목록을 볼 수 있음 | 수익성 질문을 자동 계산으로 읽기 | 자동 결과와 원 표의 매출, 이익을 대조한다 |
| 16 | 수익성 자동 결과를 의심할 수 있음 | 신용 위험 질문 | 위험 점수와 부채, 현금흐름의 연결을 말한다 |
| 17 | 여러 지표를 대조할 수 있음 | story 결과를 읽고 근거로 되돌아가기 | 문장 하나를 골라 원 표나 계산으로 검증한다 |
| 18 | 회사 안 숫자를 읽을 수 있음 | 금리와 거시 배경을 붙이기 | 회사 숫자와 macro 값의 기준 기간을 분리한다 |

## 4. 중간 삽입 정책

정렬과 URL을 분리한다. 공개 URL의 안정 키는 `topicSlug` 와 폴더명 뒤쪽 slug 다. 앞의 숫자 prefix 와
frontmatter `seriesOrder` 는 화면에 보이는 순서다. `landing/src/lib/blog/posts.ts` 는 `seriesOrder` 를
`parseInt` 로 읽으므로 `2.5`, `03a` 같은 중간 번호는 쓰지 않는다.

삽입 판단은 세 갈래다.

1. **아직 뒤 편이 발행되지 않은 구간.** 커리큘럼 번호만 다시 매긴다. 새 글을 쓸 때 폴더 prefix 와
   `seriesOrder` 를 최종 번호로 만든다.
2. **이미 발행된 뒤 편 앞에 필수 선행편을 넣어야 하는 경우.** 한 번의 기계적 정리 커밋으로 뒤 편 전체의
   폴더 prefix, `seriesOrder`, 커리큘럼 번호, 앞뒤 링크 문구를 함께 옮긴다. `topicSlug` 는 바꾸지 않는다.
   public URL 은 slug 를 쓰므로 prefix 변경 자체로 URL이 깨지지 않는다.
3. **필수 선행편이 아니라 보충 설명인 경우.** 중간 번호를 억지로 만들지 않는다. 현재 트랙 끝이나 전체 끝에
   보충편으로 발행하고, 본문 내부 링크와 `relatedPosts` 로 해당 지점에 걸어 둔다.

끼워 넣기 전 질문 세 개를 통과해야 한다.

- 이 편을 안 읽으면 다음 편의 행동 검사를 실패하는가?
- 기존 편 한 문단이나 그림으로 흡수하면 충분하지 않은가?
- 새 공개 호출계약이나 브라우저 실행 경계를 추가로 검증해야 하는가?

셋 중 첫째가 아니고 둘째가 맞으면 삽입하지 않는다. 셋째만 맞으면 8절 TODO 에 보류하고 실행 검증 뒤 결정한다.

  `wrapLastExpression` 의 정규식 `^[a-zA-Z_]\w*[\[.].*=` 가 괄호 안 키워드 인자(`freq="Y"`)를 대입문으로
  오인해 마지막 식을 통째로 버렸다. 오류도 안 나고 빈 출력이라 아무도 몰랐다.
  괄호 깊이를 세는 스캐너로 교체했다(`pyodideWorker.ts`).

아직 안 닫은 것은 7절 체크리스트와 8절 TODO 로 넘겼다.
